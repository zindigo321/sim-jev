# 第一阶段模型假设、事件与指标口径

本模型是用于检查任务—故障—维修—备件耦合的科研软件原型。
所有默认参数都是合成示例，不是论文严格复现参数，不是实际机队校准或验证结果。
时间单位为小时；飞机小时与等待飞机小时为不同的累计量。

## 1. 实体、状态和简化范围

飞机有唯一 ID，状态互斥：`idle`（空闲）、`flying`（执行任务）、
`waiting_repair`（故障待修）、`repairing`（维修中）。每机仅一个关键可更换部件。
所有飞机同型、初始空闲；不模拟基地间转场、机组、燃油、天气、定检或共因故障。

任务输入为 ID、固定开始时刻、正持续时间、正需机数、非负价值。
随机任务按泊松到达产生，持续时间与价值分别均匀抽样，需机数为离散均匀。
第一项随机任务在一个指数间隔后到达；不是强制在 t=0 开始。
显式任务列表允许输入评价期以后的任务，其状态保留为 `pending`，不计入已提供任务。

只有空闲飞机可派，按字符串 ID 排序，资源足够才整项派出。
资源不足的任务记 `not_executed`，不延期、也不部分执行。
成功获得完整价值，失败/未执行/未结束均暂不获得价值；不建模成本、罚金或部分价值。

每架参飞机全程执行同一任务。一个故障使整个任务立即失败，健康参飞机立即空闲，
故障飞机立即可请求地面维修。本阶段不模拟返航、迫降、救援或故障诊断延迟。

## 2. 飞行寿命、实际暴露及失效事件

部件寿命以飞行小时计，指数分布均值为 `1 / failure_rate_per_flight_hour`。
危险率为 0 时寿命为无穷，不安排故障事件。
每个事件间隔只给 `flying` 飞机增加实际飞行小时。
任务中止会立刻停止所有参飞机暴露，不消耗原计划剩余飞行时间。
待修及维修中保留失效后的零寿命，只有维修完成才按故障随机流抽取新寿命。

每次派机与释放任务都改变飞机版本；故障事件带派机时的版本号。
任务结束、换件或其他任务中止后，旧版本事件只写 `stale_event` 审计日志，不改变业务状态。
失败任务的结束事件同样失效；不可能随后再成功。

飞行中的剩余寿命由该次飞行固定的故障时刻减当前时刻计算，避免分段运行逐次扣减的舍入
把故障推过任务结束/截止边界。双精度实际事件时间严格相等时才按同刻顺序处理；
不人为把相邻但不同的浮点时刻合并。

## 3. 同时刻事件顺序

队列键为 `(time, priority, sequence)`，序号是本次模拟内部单调整数，不依赖墙钟或 UUID。

| 优先级 | 事件 | 含义 |
| --- | --- | --- |
| 0 | 故障 | 恰在任务结束时故障仍算失败 |
| 1 | 维修完成 | 释放机位并恢复飞机可用 |
| 2 | 订单到货 | 增加在库备件 |
| 3 | 任务结束 | 无故障的整项任务成功并释放飞机 |
| 4 | 尝试维修 | 等待飞机在有件有位时开始维修 |
| 5 | 补货检查 | 按当前库存位置下单 |
| 6 | 任务开始 | 用此时已经释放的空闲飞机派机 |

同类事件按入队序号；初始任务先按开始时刻、任务 ID 排序后入队。
事件可产生同刻新事件，新事件重新进入优先队列。例如零维修时长会同刻完成，
零交期会同刻到货，任务开始时零剩余寿命会同刻故障。
优先级约束作用于当时已在队列中的事件，不会把尚未发生的因果事件提前。

同任务多机精确同时失效时，首次故障处理会收集该任务所有此刻到寿命的参飞机，
全部进入维修请求，任务仍只失败一次。其他对应故障事件因版本变化失效。
维修完成及到货事件检查实体状态，重复事件不再次释放机位、补库存或增加维修计数。

## 4. 维修、备件和等待时间

维修按 `(requested_at, repair_id)` 先到先修；同型部件，无优先任务插队。
一个维修占一个机位，在真正开始时消耗一件备件。维修时长取配置区间的均匀分布。
缺件不占机位。完成后报废的旧部件不进入修复回收流程。
允许零机位表示保障能力关闭；允许零维修时长表示即时换件的边界情景。

`unmet_demand` 定义为所有尚未开始维修的请求数；即使仓库已有件但没有机位，也仍计入。
它是待满足的维修用件需求，并不等同于物理缺货数量。

```text
库存位置 IP = on_hand + in_transit - unmet_demand
订购数量 Q = max(0, reorder_target - IP)
```

维修开始使在库量和待修需求同时减少 1，不改变 IP。
到货使在途减少、在库增加，也不改变 IP。下单立即增加在途，因此后续检查不对同一缺口重复下单。
目标 0 表示不保有额外库存，不表示停止补货；存在待修缺口仍会订购。
初始在库可以高于目标，不自动丢弃或退货。

补货检查发生于 t=0、检查周期、两倍周期……直到并包含截止时刻。
不在每次故障时额外触发补货，故障可能需要等下次检查。
每笔订单独立记录数量和唯一 ID。交期在订购时由供货随机流抽取，
**下单时即公开准确的预计到货时刻，之后没有额外延误**。
因此观测中的订单 ETA 是已知承诺。未来阶段若增加隐蔽供货延迟，必须将 ETA 与真实到货事件分开。
到货后立即检查维修队列；仓容与外部供给能力假定无限。

等待时间按每个事件间隔分类：在 FIFO 队列中，前 `min(on_hand, 等待数)` 个请求
视作可由库存覆盖，累计 `bay_wait_hours`；其余累计 `spare_wait_hours`。
这只是统计上的库存分配，不提前扣件；每个请求每个时段只计一类。
两种累计之和等于“从故障请求到维修开始或当前截止”的总等待飞机小时。
维修服务时长不计为等待，缺件与无机位同时发生时，以该 FIFO 库存分配口径归因。

## 5. 截止与可用度

`run(until=T)` 处理所有 `time <= T` 的事件（包括其生成的同刻事件），随后停止。
最后一个事件到 T 的区间仍进行积分；不为清空队列而处理 T 之后的事件。
恰在 T 开始但没有结束的任务是 `running`；恰在 T 结束的任务按事件规则成功或失败。
期末待修、维修中、在途订单均保持状态。

可用飞机数是 `idle + flying`；故障待修和维修中不可用。
可用度 `∫可用飞机数 dt / (飞机总数 × 已评价小时)`。
空闲比例另用 `∫空闲飞机数 dt` 作分子，不能与可用度互换。
完整运行的分母是 `fleet_size × horizon_hours`；分段运行汇总的分母是当前已推进时长。
在 t=0 尚无时间分母时两种比例输出 JSON `null`。

## 6. 汇总指标字段

下表中的 T 是 `elapsed_hours`；所有计数只包含截至 T 已实际处理的事件。

| 字段 | 单位、分母与截止口径 |
| --- | --- |
| `missions_offered` | 项，已到固定开始时刻且已处理启动决策的任务 |
| `missions_success/failed/not_executed/unfinished` | 项，分别成功/执行失败/未执行/仍执行；四项之和=offered |
| `missions_future` | 项，未到提供时刻的 pending 任务，不计入 offered |
| `mission_success_rate` | success / offered；无提供任务时为 null |
| `mission_value_offered` | 合成价值点，offered 任务价值之和 |
| `mission_value_earned` | 价值点，仅成功任务价值 |
| `mission_value_failed/not_executed/unfinished` | 价值点，各类任务对应价值；与earned相加=offered价值 |
| `mission_value_capture_rate` | earned / offered价值；分母为0时null |
| `flight_hours` | 飞机小时，所有飞机截至T实际飞行时长之和，含中止前及期末仍飞行部分 |
| `failures` | 次，实际坏机次数；一次任务失败可能对应多个同时坏机 |
| `repairs_started/repairs_completed` | 次，截至T已开始/完成的换件维修；期末在修不计完成 |
| `spare_wait_hours` | 等待飞机小时，FIFO库存未覆盖的时间积分，含期末尚未开始维修的等待 |
| `bay_wait_hours` | 等待飞机小时，FIFO库存已覆盖但尚未开始维修的时间积分 |
| `total_repair_wait_hours` | 等待飞机小时，上述两类之和；不是平均等待、也不含维修服务时间 |
| `available_aircraft_hours/idle_aircraft_hours` | 飞机小时，分别对可用/空闲飞机数积分至T |
| `availability/idle_fraction` | 无量纲，分别以上述积分除以fleet_size × T |
| `ordered_quantity/arrived_quantity` | 件，截止前累计下单/到货数量，不是订单笔数 |
| `on_hand/in_transit` | 件，期末在库/未到货数量；库存与在途分开报告 |
| `unmet_demand/inventory_position` | 件，期末待修用件需求/在库+在途−需求 |
| `aircraft_idle/flying/waiting_repair/repairing` | 架，截止状态计数，总和=机队规模 |
| `orders_in_transit` | 笔，截止尚未到货订单数 |

每架飞机、每项任务的飞行小时与总指标守恒；库存满足
`期末库存 = 初始库存 + 累计到货 − 已开始维修次数`，
在途满足 `累计订购 = 累计到货 + 期末在途`。
引擎在每个事件后检查资源容量、库存、飞机状态和任务归属等不变量。

## 7. 随机性、信息边界及导出

四条流依次为任务、故障、维修、供货，使用固定顺序的 `SeedSequence.spawn(4)`。
不使用全局随机数；稳定排序、局部整数 ID 和序列化顺序保证相同环境下重复输出。
区间上下限相等时直接使用固定时长/价值，不消耗该抽样。
不保证跨 NumPy 版本逐位一致，输出记录依赖版本；跨策略共同随机数设计留到后续阶段。

任务在开始时公布，`get_observation` 不暴露未来未公布任务、实际部件剩余寿命、
维修随机完成时刻、随机流状态和事件队列；它是独立构造的数据，不返回可变实体引用。
订单准确 ETA 属于已公开信息；已开始任务的计划时长属于已知任务信息。

`export_state`/`state.json` 是内部审计记录，包含隐藏寿命、未来队列、随机流状态和输入任务，
不可传给规划策略。无限寿命在 JSON 中编码为 null；`resume_supported=false`。
以上为保留的旧审计导出含义。阶段2A另实现 `to_checkpoint/from_checkpoint` 和文件读写，
使用严格独立的 `InternalCheckpoint` schema v1；它保留无限寿命标签、完整日志/history及reset输入，
经验证可恢复同一执行世界。`clone()` 同样只用于内部重放，不代表合法候选预测情景。
分支间实体键控共同随机数、周承诺和合法规划输入仍仅有设计契约，见
[RESEARCH_CONTRACT.md](RESEARCH_CONTRACT.md)；验收见 [PHASE2A_VALIDATION.md](PHASE2A_VALIDATION.md)。

## 8. 合法零值与拒绝输入

- 随机到达率为0、或显式空任务列表：没有任务，仍可进行库存检查与积分。
- 故障率为0：默认寿命无限，正常任务不故障；确定性实验可另给初始寿命。
- 库存为0：合法，无件时等待；目标和待修需求决定后续补货。
- 机位为0：合法，等待不自动消失；维修时长/交期为0：合法，同刻完成/到货。
- 飞机数至少1、任务需机数至少1，需机数大于机队数合法但该任务会未执行。
- 评价时长、任务时长、补货周期必须正数；率、价值、库存等必须非负。
- 数量及seed必须整数（拒绝bool），所有常规数值必须有限，上下限不能倒置。
- 未支持的配置字段直接报错。危险率不是概率，不限制到[0,1]；不存在可静默接受的概率字段。

极端到无法以双精度区分的任务到达/检查间隔会明确报错。
本模型面向小规模科研原型，未针对极大机队或极高事件密度做性能承诺。
