## 1. 基准身份、配置和参考运行

## 2. 四种信息对象的权限

| 对象 | 可含信息 | 禁止用途/约束 | 本轮状态 |
| --- | --- | --- | --- |
| `InternalCheckpoint` | 完整配置、reset 输入、真实飞机/任务/维修/订单状态、库存、真实剩余寿命、failure_due_at、未来队列及序号、四流 RNG 状态、指标、全部业务日志及 history | **永远不能直接作为可部署规划器输入。** 仅供内部恢复、审计、同世界重放；其访问权限高于策略 | 实现严格 JSON 恢复与 clone |
| `PolicyObservation` | 当前时刻；已知飞机状态/占用/实际已飞小时；已公布任务及其已发生结果；维修请求、已发生开始/完成和等待；当前库存、已确认订单及公开 ETA；当时已经公布的规则 | 无真实寿命、真实未来故障/维修完成事件、未来未公布任务、执行 RNG、队列；规则必须带公布时刻与生效时刻（新增规则机制时） | 当前由 `get_observation()` 提供；没有 PHM 或周窗口 |
| `PlanningInput/Belief` | PolicyObservation 的独立副本；已公布规则/能力；合法可得的预测模型、先验或基于截至当时观测更新的后验；过去合法观测/行动历史；模型及信息来源版本 | 不携带真实寿命、真实未来事件或执行 RNG；不能从 checkpoint 摘除几项字段就认定合法；信念更新不得条件于未公开内部值 | 本轮只定义契约，无可运行规划器接口 |
| `PlanningScenario` | 由 PlanningInput/Belief 与**独立预测随机源**生成的可能未来；带预测域、情景 ID、模型版本及父合法输入哈希 | 不复制执行未来；不能 clone 真世界后改 seed 冒充预测；候选之间可共享同一预测情景，但不能消耗/修改主执行 RNG | 本轮不实现 |

当前准确订单 ETA 是下单时公开的承诺，不是信息泄漏；当前没有确认后的隐藏延误。若后续增加随机延误，应分别保存 `promised_eta`（可观察）和真实实现时刻（内部），并通过到货事实更新观察。维修 `due_at` 当前属于内部状态，没有向观测公开。即便任务在 episode 构造时全部生成，当前模式也只在开始时公布；未来周模式只能公布规定窗口，不能因任务已在内存而提前暴露。

`clone()` 与恢复仅保证可变实体、队列、日志、history、指标和 RNG 深度隔离，保留同一个已抽定世界的隐藏信息。分支推进、修改分支或消费其 RNG 不得影响父实例；导出字典同样不得反向修改原实例。这是工程重放能力，不代表合法预测或跨策略公平性。

## 3. 内部恢复契约

必须在 `run(until=t)` 已处理完 `t` 时刻全部因果事件后保存稳定边界；t=0 也先调用 `run(until=0)` 处理零时刻初始化事件。handler 中间、尚有同刻因果链未处理、或发生异常导致半状态时不得导出可恢复 checkpoint。`run` 已到指定时刻后，下一待处理事件须严格晚于当前时刻；720 后的已排事件可保留，不清空来伪装完成。

checkpoint 必须包含所有运行状态与 reset 所需输入，恢复不得调用 reset、重采样或重新生成任务以替代恢复。`missions=None` 意味默认随机输入，`missions=[]` 意味明确无任务；显式任务和初始寿命 override 必须被记录，恢复后的 reset 维持这些区别。reset(seed=...) 是另一次从输入开始的实验，不是从 checkpoint 接着走。

schema 1 的 `infinity_encoding="positive-infinity-tag-v1"` 将正无穷寿命编码为 JSON 对象 `{"$float":"+inf"}`，恢复为正无穷；只允许飞机 `remaining_life_hours` 和 reset 输入 `initial_lifetimes` 使用该标记。非法 NaN、负无穷及普通字段的无穷必须拒绝。`state.json`/`export_state()` 仍是历史审计导出，`resume_supported=false`；其 null 编码不可被猜测性导入。新 checkpoint 不使用 pickle。

恢复须校验版本、必要字段、枚举、时刻域、引用关系、数量和容量、库存/在途守恒、各类账本及 RNG 状态。损坏数据报带字段路径的错误，不静默修补或猜测。这些检查验证结构和内部一致性，不是来源真实性签名；文件 SHA256 能检测字节差异，也不能单独证明来自可信执行。未知版本本轮直接拒绝，无跨任意旧版本迁移承诺。运行环境/依赖版本需记录；不承诺跨任意 NumPy 版本的随机位流一致性。

完整业务 events 日志（含 stale_event）必须连续、逐条、同顺序一致；任务分类、事件时刻、终态所有权、订单/维修离散账本和整数计数严格比较。积分及累计飞行/等待等允许浮点累加误差：`rel_tol=1e-12, abs_tol=1e-10`，不为通过验收放宽边界分类或事件顺序。history 可能因无事件暂停而多一行状态采样，只能在确认其不是业务事件所需记录、且相邻区间状态不变时删除纯采样冗余行；不能删业务日志，也不能凭最终摘要相近跳过轨迹核验。

## 4. 后续周级模式的时间与承诺契约（2B，尚未实现）

本节是明确命名的新周模式设计，不改变 `synthetic-single-lru-v1` 现有行为。旧模式继续处理 `time<=720` 的任务开始事件，恰在 720 开始可为 running/failed/not_executed。新模式只提供 `start_time<720` 的任务；显式输入中恰在 720 开始或更晚的任务保留 pending，不进入 offered，也不成为最后一周候选。

决策点为 0、168、336、504、672 h。第 k 次公布其开始时刻落入 `W_k=[t_k,min(t_k+168,720))` 的全部任务，末段 48 h。每个合法任务由**计划开始时刻**唯一决定 offer 窗口：开始于 168 的任务归第二窗，开始于 167.999... 的归第一窗，不因完成时刻或浮点邻近而改窗。论文第 6 页 §3.2 末窗写 `[672,720]`；本项目选 `[672,720)` 是研究者约定，不宣称逐字复现。计时原点不预设日历星期；周/日指令分别指 168 h 和 24 h 节拍。

跨周任务只承诺一次，原承诺持续到该任务终结或评价截止；新周不能再次接纳、取消或重新计入 offered。新周规划读取其当前占用作为约束。截止仍执行任务保持 unfinished，不算成功或失败；不在 720 强行清队列。720 时仍处理已存在的故障、任务结束、到货、维修完成及其同刻物理后果：恰在 720 完成的任务可以成功，同刻故障优先仍失败。其后不执行新周决策或启动恰在 720 的任务。

同刻次序采用明确的阶段屏障（将在新版本实现并单独测试）：

1. 积分至 t，先处理此前已排的物理事件及它们产生的同刻物理因果链；内部沿用故障、维修完成、到货、任务结束、尝试维修的物理优先级。不得将两个相邻但不相等的浮点时刻合并。
2. 公布在 t 生效的规则更新与当期窗口任务，再构造合法观测。每条规则记录 `announced_at`、`effective_at`、适用窗口和版本；预先公开的未来规则可以读取，未公布规则不能偷看。既有已承诺任务不受事后规则追溯取消，新增规则默认约束新承诺；若研究紧急追溯规则，必须另定义版本和失败归因。
3. 若 t 是周点且 t<720，执行唯一一次周级承诺并持久化决策；若也是日点，随后固定日执行器读取最新周承诺和公开规则，安排派机/维修/补货。日点为 0、24、...、696，不在 720 发新日指令。
4. 执行当时的任务开始等动作及其因果事件，直到 t 再次稳定。零寿命任务可在派机之后同刻故障，零维修/交期可同刻完成；新因果事件不被提前到其原因之前。

此屏障是后续设计，不能只给 WEEKLY_COMMAND 一个数值优先级便宣称所有因果链已正确排序。必须区分决策前物理闭包和决策后动作闭包。当前补货处理器及其优先级不改。

接纳/拒绝由周级策略唯一负责，日执行器不得再次独立接纳，也不能以资源不足把任务从需求账本删除。拒绝任务记 rejected；已承诺但到开始时无法派出记 accepted_not_executed；执行中失败记 failed；执行中为 running；全部参飞机完成才 success。下一阶段可另设新账本字段，不覆盖旧 summary 的四分类语义。

## 5. 后续计数、窗口账本、在线评分与结算

对每个窗口固定 offer 集 `O_k`，周决策固定 accepted 子集 `A_k`，拒绝集为 `O_k\A_k`。`offered_count=|O_k|`、`accepted_count=|A_k|`、`offered_value=sum(v_j,j∈O_k)` 在 offer/commit 时冻结，拒绝不会改变分母。这里 v_j 仍为已声明价值单位；若改成 k$/AFH 需另版定义任务总可实现价值，不能直接把密度求和冒充总价值。

每项任务有稳定 `mission_id`、`offer_window_id`、承诺和结果；每项终局结果在账本最多登记一次。若第一窗的任务在第二窗成功，于**实际完成时刻**向第一窗 cohort 成功计数/价值补记，而不是只记第二窗，亦不能因为第一窗已经结束就丢弃。全周期汇总按 mission_id 去重，各 offer 窗口最终分子相加应恰等于全域分子；允许记录截至 720 仍 unresolved 的任务，但不能把尚未完成的未来成功提前算入。

| 数量/率 | 分子/分母及窗口归属 | 零分母及截止规则 |
| --- | --- | --- |
| offered、accepted、rejected | O_k、A_k、O_k\A_k 的唯一任务数 | 无任务均为 0；拒绝仍在 offered |
| success、failed、accepted_not_executed、unfinished | 属于 O_k 的已接纳任务截至统计时刻实际结果 | 四者之和=accepted；再加 rejected=offered；未开始但已承诺者计 unfinished 并另设 pending_execution 子类 |
| DSR/cohort_success_rate | O_k 中已成功任务数 / offered_count | 0 分母输出 null；未决任务仍占分母 |
| RCR/cohort_value_capture | O_k 中已成功获取价值 / offered_value | 价值分母 0 时 null；不得删除零价值任务的计数需求 |
| ASR/cohort_accepted_success | A_k 中已成功任务数 / accepted_count | 0 分母 null；不是 success / 已经结束的任务 |
| acceptance_rate | accepted_count / offered_count | 0 分母 null；仅诊断，不作为完成率 |
| 全 720 h DSR/RCR/ASR | 各窗口最终累计分子之和 / 相应冻结分母之和 | 先累加再相除；绝非五个周比例平均，末窗仅 48 h |
| availability、idle_fraction | 相应状态飞机数在物理时间窗积分 / (fleet_size×实际窗口长度) | 长度 0 时 null；跨周飞机暴露按时间切分，不按任务 offer 窗口整体归属 |
| 维修/供货/实际飞行与等待 | 事件计数按实际发生时刻；连续量按实际经历时间分段积分 | 事件报告窗使用 [t_k,t_{k+1})；720 的物理完成/到货等记末窗的 terminal_boundary 子账，全文只计一次；不新 offer |
| 成本/NSE/J720 | 将来须另行冻结成本函数和单位，NSE=成本/交付价值 | 本轮没有成本模型，不填 0 假装实现；无交付价值时 NSE 需定义为 null |

须区分三种时间含义：

- **在线短窗评分**：在窗口关闭时，仅用截至当时已发生的结果计算 `DSR_k(as_of=t)`、`RCR_k(as_of=t)` 等，附 unresolved 数量和 as_of。它是暂时的已实现值，不是最终 cohort 结果，不能使用 checkpoint 中未来事件推断“已经成功”。
- **实际回报结算**：若后续采用本项目事件结算方案，任务成功时才发放对应增量（例如 `1/|O_k| + v_j/sum(O_k.value)`，分母在其 offer 时固定；零分母分项置 0 并带有效性掩码），结算时刻等于真实完成时刻，即使已跨周。已发出的 transition/reward 不无声明回写；延期归因保留原 offer_window_id，后续训练必须显式选择可处理延迟结算的算法/回报协议。失败、拒绝、未执行没有成功增量。此处只是无未来泄漏的结算约定，本轮不发训练奖励、不训练。
- **期末 cohort 指标**：720 处理完终点物理事件后，回看各窗口的已实际实现结果。第一窗跨周成功已补回第一窗，未完成仍 unfinished。这类报表补记不等于篡改早先在线观测或已发奖励。

论文第 11 页式(6)描述周 `DSR_k+RCR_k`，未在本处充分指定跨周终结的在线细节。上面的延迟事件结算是项目合成设计，不能宣称与论文逐周奖励等价。对每窗最终 cohort 分项增量求和可以恢复该窗最终比例，但结算时刻和折扣回报可能不同；也不能以周奖励之和替代式(7)的全周期 J720。训练前须冻结目标、信用分配、折扣和零分母掩码，不能把评价公式直接冒充已实现训练目标。

## 6. 后续实体键控随机数协议（2B，尚未实现）

当前四流仅支持相同模型、配置、输入、依赖和策略调用顺序下的复跑/恢复。固定 seed 和独立模块流没有消除跨策略的抽样错位，不能宣称已经实体 CRN 配对。

后续协议需要有版本的规范键编码、独立域和无状态/计数器抽样，不使用 Python 进程随机化的内置 `hash()`。建议键包含：`protocol_version / domain / scenario_id / entity_type / stable_entity_id / generation / random_purpose / draw_index`。各用途的候选定义如下，均是项目设计，不冒称论文披露了这些精确字段：

| 用途 | 稳定实体与代次示例 | 注意 |
| --- | --- | --- |
| 任务到达与属性 | scenario + 外生 arrival_index + attribute_name | 在策略外生成共同需求；不得按接纳后的位置编号 |
| 部件寿命/突发失效 | aircraft_id + component_class/slot + replacement_generation + failure_channel | 以实际飞行暴露驱动；同代同用途抽样一致，策略可改变何时消耗暴露 |
| 维修服务时长 | aircraft/component + replacement_generation + repair_attempt + service_time | 不用全局维修请求递增号作为唯一外生身份，避免其他飞机先维修改变该实体样本 |
| 采购交期/隐藏延误 | scenario + supplier + component_class + 预先定义的采购机会/外生供货实体 + purpose | 策略可改变数量和选择；同键只在有明确对应含义时配对，不能假定不同策略每笔订单天然一一对应；稳定订单键设计需在2B冻结 |
| 观测误差 | 可公布的传感观测时点 + aircraft/component + purpose | 真状态与观测噪声分域；合法信念更新只读已公布结果 |
| 规划情景 | planning_domain + 合法输入标识 + planning_scenario_id + 情景实体键 | 独立预测根种子；不能包含执行 RNG 状态或真实未来抽样值 |

策略名称、算法名称、候选在列表中的位置、评估顺序、抽样先后、线程编号、墙钟时间不得成为外生随机键。决定性的候选 ID 可作为结果索引，但不参与共同外生情景噪声取样。不同候选共享相同 scenario_id 的预测外生路径；新增、换序、重复评估不能改变已有候选结果，也不能消耗执行随机流。

配对保证限定为**可解释地对应的外生实体/代次/用途**，不承诺不同策略实际发生事件序列相同。下一阶段必须测试键碰撞/编码、候选换序与增评不变性、策略名不变性、实体分支差异、主轨迹不受评估污染，以及同一合法输入下更改隐藏执行未来不影响预测输入/候选/情景。
